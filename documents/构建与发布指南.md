# Bee-Plus 组件库构建与发布指南

本文档详细记录了 Bee-Plus 组件库的构建系统搭建过程、工具选型决策、配置详情、遇到的问题复盘，以及发布到 NPM 的操作流程。

---

## 1. 构建工具选型：Rollup

在构建组件库（Library）时，我们选择了 **Rollup** 而非 Webpack 或 Vite（Vite 生产环境底层也可以使用 Rollup），主要基于以下原因：

1.  **代码纯净度**：Rollup 生成的代码非常简洁，没有像 Webpack 那样大量的模块加载样板代码（Runtime Boilerplate）。这对于作为依赖包分发的组件库来说至关重要，能有效减小包体积。
2.  **ESM 标准支持**：Rollup 是 ES Module 打包的先驱，能够完美生成 ESM 格式产物，支持 Tree Shaking（按需加载），这是现代前端开发的标准。
3.  **生态成熟**：Vue 3 源码、Element Plus 等主流开源库均使用 Rollup 进行构建。
4.  **插件灵活性**：通过组合 `rollup-plugin-vue`、`rollup-plugin-postcss` 和 `esbuild`，我们可以精准控制每一类文件的编译过程。

## 2. 环境搭建与配置

### 2.1 安装依赖

我们需要安装 Rollup 核心及处理 Vue、TS、CSS 的相关插件。为了提升编译速度，我们引入了 `esbuild`。

```bash
pnpm add -D -w rollup @rollup/plugin-node-resolve @rollup/plugin-commonjs rollup-plugin-vue rollup-plugin-postcss sass vue-tsc esbuild rollup-plugin-esbuild
```

*   `rollup-plugin-vue`: 编译 `.vue` 单文件组件。
*   `rollup-plugin-esbuild`: 使用 esbuild 极速编译 TS 和 JS 代码。
*   `vue-tsc`: 专门用于生成 `.d.ts` 类型声明文件（Rollup 只负责打 JS 包，不负责生成类型）。

### 2.2 目录结构调整

为了支持统一导出，我们在 `packages/bee-plus` 下创建了发布主包：

```text
packages/bee-plus/
├── defaults.ts      # 默认导出（Vue Plugin）
├── index.ts         # 总入口，导出所有组件和默认插件
└── package.json     # 发布包的配置
```

### 2.3 配置文件：rollup.config.mjs

我们在根目录创建了 `rollup.config.mjs`，关键配置如下：

```javascript
import resolve from '@rollup/plugin-node-resolve'
import commonjs from '@rollup/plugin-commonjs'
import esbuild from 'rollup-plugin-esbuild'
import vue from 'rollup-plugin-vue'
import postcss from 'rollup-plugin-postcss'

export default {
  input: 'packages/bee-plus/index.ts', // 统一入口
  output: [
    {
      format: 'es',
      file: 'packages/bee-plus/dist/index.mjs', // ESM 格式
      sourcemap: true,
    },
    {
      format: 'cjs',
      file: 'packages/bee-plus/dist/index.js',  // CJS 格式
      exports: 'named',
      sourcemap: true,
    }
  ],
  external: ['vue'], // 核心：排除 Vue，避免打包重复
  plugins: [
    vue(), // 处理 Vue 文件
    esbuild({ // 用 esbuild 处理 TS/JS
      target: 'esnext',
      loaders: {
        '.vue': 'ts', 
      }
    }),
    postcss({ // 提取 CSS
      extract: 'index.css',
      minimize: true
    }),
    resolve(),
    commonjs()
  ]
}
```

## 3. 遇到的问题与复盘

### 问题 1：Rollup 配置与 Typescript 插件的冲突
**现象**：
最初使用 `@rollup/plugin-typescript` 时，报错 `RollupError: ... Expected ',', got '{'`。
**原因**：
Rollup 的 TS 插件在处理 `.vue` 文件导入时，如果配置不当，会无法正确识别非 `.ts` 文件。且纯 TS 编译速度较慢。
**解决**：
我们切换到了 **`rollup-plugin-esbuild`**。Esbuild 速度极快，且对混合文件类型的处理更为宽容和简单。类型生成工作单独交给 `vue-tsc` 处理。

### 问题 2：产物路径混乱
**现象**：
最开始构建产物直接生成在根目录 `dist`，与 `packages/bee-plus` 的发布结构脱节。
**解决**：
修改 `rollup.config.mjs` 和 `package.json`，将输出路径统一指向 `packages/bee-plus/dist`，确保发布包内部包含所有必要文件。

## 4. NPM 发布实操指南

### 场景一：第一次发布
如果你是首次将 `bee-plus` 发布到 NPM，请严格按照以下步骤操作：

1.  **检查包名可用性**：
    *   NPM 包名必须全球唯一。请务必修改 `packages/bee-plus/package.json` 中的 `name` 字段（例如 `@your-username/bee-plus`），否则很大几率会发布失败（403 Forbidden）。

2.  **构建项目**：
    *   在**项目根目录**运行：
    ```bash
    npm run build && npm run build:types
    ```

3.  **登录 NPM**：
    *   在终端运行：
    ```bash
    npm login
    ```
    *   按提示输入用户名、密码和邮箱（验证码会发到邮箱）。

4.  **执行发布**：
    *   **必须切换到发布包目录**：
    ```bash
    cd packages/bee-plus
    ```
    *   执行发布命令（如果是 `@` 开头的包名，必须加 `--access public`）：
    ```bash
    npm publish --access public
    ```

---

### 场景二：后续更新发布
当你有代码更新需要发布新版本时，流程如下：

1.  **修改代码与构建**：
    *   修改组件代码后，在**项目根目录**重新构建：
    ```bash
    npm run build && npm run build:types
    ```

2.  **更新版本号**：
    *   **切换到发布包目录**：
    ```bash
    cd packages/bee-plus
    ```
    *   根据更新类型选择一个命令执行（它会自动修改 package.json 并生成 git tag）：
    ```bash
    # 修复 Bug (例如 1.0.0 -> 1.0.1)
    npm version patch

    # 新增功能 (例如 1.0.0 -> 1.1.0)
    npm version minor

    # 破坏性更新 (例如 1.0.0 -> 2.0.0)
    npm version major
    ```

3.  **发布新版本**：
    *   执行发布命令：
    ```bash
    npm publish
    ```

### 4.4 NPM 发包可能会遇到的问题

整理了实操过程中遇到的高频问题及解决方案：

#### 1. 样式未打包（发布后无样式）
*   **现象**：
    在其他项目中使用包时，组件功能正常但完全没有样式，检查 `dist/index.css` 发现文件为空或体积过小（仅几KB）。
*   **原因**：
    Rollup 的入口文件（`index.ts`）通常只导出了 JS 组件（`.vue` / `.ts`），如果没有显式引入样式文件，打包工具就不会去处理样式。
*   **解决**：
    在入口文件 `packages/bee-plus/index.ts` 中显式引入全局样式入口：
    ```typescript
    import '@bee-plus/theme-chalk/index.scss'
    ```

#### 2. 图标丢失（显示为空白方框）
*   **现象**：
    样式生效了，但图标（icon）显示为方框。
*   **原因**：
    CSS 中使用了相对路径引用字体文件（如 `url("./fonts/element-icons.woff")`），但 Rollup 默认只编译 JS/CSS，不会自动把字体文件从源码目录复制到发布目录 (`dist`)。导致 CSS 引用的路径下找不到文件。
*   **解决**：
    安装 `rollup-plugin-copy` 插件，将字体文件夹原样复制到 `dist` 中：
    ```javascript
    // rollup.config.mjs
    copy({
      targets: [{ src: 'packages/theme-chalk/fonts/*', dest: 'packages/bee-plus/dist/fonts' }]
    })
    ```

#### 3. 权限报错 (403 Forbidden - 2FA)
*   **现象**：
    发布时报错 `E403 ... Two-factor authentication ... is required`。
*   **原因**：
    NPM 现在的安全策略强制要求发布新包必须开启 **2FA (双重认证)**。
*   **解决**：
    登录 npmjs.com 官网，在头像 -> Account Settings 中开启 2FA（通常需要绑定 Authenticator App）。开启后重新 `npm login`，发布时根据提示输入 OTP 验证码。

#### 4. 版本重复报错
*   **现象**：
    报错 `You cannot publish over the previously published versions`。
*   **原因**：
    NPM 禁止覆盖已发布的版本。
*   **解决**：
    运行 `npm version patch` 升级版本号后再发布。

#### 5. 淘宝镜像源无法发布
*   **现象**：
    登录或发布时卡住或报错。
*   **解决**：
    必须切换回官方源才能发布：
    ```bash
    npm config set registry https://registry.npmjs.org/
    npm login
    ```

### 4.5 分支合并与发布实操 (Release/Online)

当你完成了开发（在 `1.0.0` 或其他 Feature 分支）并准备发布时，请遵循以下标准流程将代码合并到 `release/online` 分支以触发自动发布：

1.  **准备发布分支**（如果是第一次）：
    ```bash
    git checkout -b release/online
    git push -u origin release/online
    ```

2.  **合并与发布流程**：
    
    *   **Step 0: 切回开发分支提交代码**
        ```bash
        git checkout 1.0.0
        git add .
        git commit -m "docs: ready for release"
        git push origin 1.0.0
        ```

    *   **Step 1: 切换到发布分支**
        ```bash
        git checkout release/online
        ```

    *   **Step 2: 合并开发分支代码**
        ```bash
        git merge 1.0.0
        ```

    *   **Step 3: 推送触发发布**
        ```bash
        git push origin release/online
        ```
    
    *   *(可选) Step 4: 切回开发分支继续工作*
        ```bash
        git checkout 1.0.0
        ```

#### 6. CI/CD 自动发布报错 (EOTP / 403 Forbidden)
*   **现象 1 (EOTP)**：
    GitHub Actions 报错 `npm error code EOTP ... This operation requires a one-time password`.
    *   **原因**：使用的 NPM Token 没有跳过 2FA (双重验证)。
    *   **解决**：生成 Granular Access Token 时，务必勾选 **"Bypass two-factor authentication (2FA)"**。

*   **现象 2 (403 Forbidden)**：
    GitHub Actions 报错 `403 Forbidden - You may not perform that action with these credentials`.
    *   **原因**：Granular Token 的权限范围 (Score) 配置错误。例如你的包名是 `bee-plus` (无 Scope)，但 Token 只勾选了 `Only select packages: @username`。由于包名不匹配 Scope，导致无权写入。
    *   **解决**：
        1.  生成 Token 时，Packages 权限选择 **"Read and write"**。
        2.  Select packages 建议直接选择 **"All packages"** (最稳妥)，或者确保手动选中的列表里包含了你要发布的那个具体包名。

## 5. 进阶：发布控制与版本管理

### 5.1 白名单与黑名单机制

NPM 提供了两种方式来控制发布文件的范围：

1.  **白名单（推荐）：`package.json` 中的 `files` 字段**
    
    *   **作用**：只允许列表内的文件发布。
    *   **【当前项目已配置】**：我们在 `packages/bee-plus/package.json` 中配置了 `"files": ["dist"]`。

    **为什么这样做？**
    对于你的项目，白名单 (`files`) 是必须且最佳的方案。

    如果不配置这个白名单，当你运行 `npm publish` 时，NPM 会把 `packages/bee-plus` 目录下的所有杂七杂八的文件全都传上去，比如：
    *   ❌ `defaults.ts` (源码，不需要发)
    *   ❌ `index.ts` (源码，不需要发)
    *   ❌ 潜在的测试文件、临时文件等

    配置了白名单后，NPM 只会上传：
    *   ✅ `package.json` (默认包含)
    *   ✅ `README.md` (默认包含)
    *   ✅ `LICENSE` (默认包含)
    *   ✅ `dist` 文件夹 (我们指定的)

    其他所有文件都会被自动屏蔽。所以你不需要再去写 `.npmignore` 黑名单文件了，目前的配置已经是“最干净”的状态。

2.  **黑名单：`.npmignore` 文件**
    *   作用：排除指定文件。
    *   如果**没有**配置 `files` 字段，NPM 默认会参考 `.npmignore`（如果没有则参考 `.gitignore`）来排除文件。
    *   缺点：容易遗漏，导致将敏感文件（如 `.env`）或垃圾文件发布出去。如果你已经配置了 `files`，通常不需要这个文件。

### 5.2 版本控制规范

软件发布需遵循 **Semantic Versioning (语义化版本)** 规范：`主版本号.次版本号.修订号` (Major.Minor.Patch)，例如 `1.0.0`。

*   **Patch (修订号)**：`1.0.0` -> `1.0.1`。用于**Bug 修复**，不改变现有 API，向下兼容。
*   **Minor (次版本号)**：`1.0.0` -> `1.1.0`。用于**新增功能**，但是 API 向下兼容。
*   **Major (主版本号)**：`1.0.0` -> `2.0.0`。用于**破坏性更新**（Breaking Changes），不兼容旧版。
